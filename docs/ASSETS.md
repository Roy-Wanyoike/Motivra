# Motivra asset-sourcing convention — Pexafy licensed-asset pipeline

**Governing issue:** [#196](https://github.com/Roy-Wanyoike/Motivra/issues/196) — owner decision recorded 2026-10-28. Supersedes the earlier tool-neutral stance from the #147 review thread.
**Applies to:** every UI-surface issue that ships imagery — #123, #124, #125, #126, #128, #147, #163 and successors.
**Licence ledger:** [`docs/assets/ASSETS.md`](assets/ASSETS.md) — one row per shipped asset, appended in the same PR that ships the asset.

Pexafy semantic image search is the adopted licensed-asset sourcing pipeline for all Motivra UI surfaces. It returns licensed photos (Unsplash/Pexels/Pixabay sources) with per-image licence metadata, which makes licence capture and self-hosting mechanical instead of ad-hoc.

---

## 1. Pipeline (binding for all UI-surface issues)

1. **Query** — describe the scene in one sentence and run it as a semantic search against the Pexafy API. Example from #196: *"mechanic kneeling by a broken-down car on a roadside"*. Semantic queries beat keyword lists: describe subject, action, setting.
2. **Licence capture** — record the per-asset licence metadata (source site, licence, author, query, source URL) as a row in [`docs/assets/ASSETS.md`](assets/ASSETS.md) **at PR time**. A PR that ships an asset without its ledger row is incomplete.
3. **Download → optimize → self-host** — download the file, convert to **WebP**, generate **responsive sizes**, and commit it under the shipping app's `public/` assets directory (e.g. `apps/customer/public/assets/…`). Size budgets from #196: **hero < 200 KB, inline < 50 KB**.
4. **Never hotlink** — Unsplash/Pexels/Pixabay *search pages* and their CDNs are never image sources at runtime. Search-page URLs quoted in issues are **inspiration only, not direct image assets** (per the #154 audit guardrails).
5. **AI-generated assets are labeled** — any asset generated by an AI model is recorded as AI-generated in the ledger and labeled where it is used. AI-generated imagery is never presented as real-world photographic evidence (vehicle inspections, incidents, workmanship).

## 2. Requesting / generating an asset (engineer workflow)

1. Write a one-sentence scene description for the surface you are building (hero, empty state, illustration).
2. Ensure `PEXAFY_API_KEY` is present **in your environment** (see §4) — never in a file you are about to commit.
3. Run the semantic search; evaluate results for subject accuracy and licence metadata completeness.
4. Download the chosen file and optimize it (WebP, responsive sizes, budgets above).
5. Commit the optimized files under the app's `public/assets/` tree and reference them from code.
6. Append the ledger row to [`docs/assets/ASSETS.md`](assets/ASSETS.md) **in the same PR**, and link the PR to the UI issue it serves.

## 3. Licence metadata contract (per shipped asset)

Each ledger row captures, at minimum:

| Field | Meaning |
| --- | --- |
| File | Committed path under the app's `public/assets/` |
| Source | Origin site of the photo (e.g. Unsplash / Pexels / Pixabay, via Pexafy) |
| Licence | The licence string returned by Pexafy for that image |
| Author | Photographer/creator attribution |
| Query | The semantic query that surfaced the asset |
| Source URL | Canonical origin URL of the image |
| Added | PR that shipped the asset |
| AI-generated | `yes` + generator/tool, or `no` |

Reviewers check ledger completeness as part of the PR checklist; assets without rows do not merge.

## 4. `PEXAFY_API_KEY` handling (security contract)

The key is registered as an encrypted **GitHub Actions repository secret** (coordinator action, 2026-10-28 — see #196). It grants read-only image search; it is still treated as a secret.

- **Consumed ONLY as an environment variable.** Tooling reads `PEXAFY_API_KEY` from the process environment at runtime.
- **Never committed** — no key material in source, docs, fixtures, `.env` files that are committed, or PR bodies.
- **Never logged** — no echoing, debugging, or printing of the variable in scripts, CI output, or issue comments.
- **Never client-bundled** — do not prefix it for frontend exposure (no `NEXT_PUBLIC_*` style reuse) and do not import it into any app bundle; asset acquisition happens outside the browser.
- **Local development** — keep the key in a local `.env.pexafy` file that is **explicitly gitignored** (guard pattern in [.gitignore](../.gitignore)), and export it into your shell environment when needed. Never copy its contents into committed files.
- **Rotation** — if the key ever leaks (commit, log, bundle, screenshot), rotate it in the Pexafy dashboard and re-register the repository secret, then verify the leak is scrubbed.
- **CI use (deferred, optional)** — CI may consume the secret for an asset-licence lint once the GitHub Actions billing lock clears (#10). No workflow file is added while that lock stands (see #154 governance note).

### Proposed: §4c. Adding a licensed UI asset (Pexafy pipeline, issue #196)

| Step | Action |
| --- | --- |
| 1 | Write a one-sentence scene description; confirm `PEXAFY_API_KEY` is set in the environment (`echo` of its *presence*, never its value). |
| 2 | Run the Pexafy semantic search; pick a result whose licence metadata is complete. |
| 3 | Download and optimize: WebP, responsive sizes, hero < 200 KB / inline < 50 KB. |
| 4 | Commit the files under `<app>/public/assets/…` and reference them from the UI code. |
| 5 | Append the licence row to `docs/assets/ASSETS.md` **in the same PR**. |
| 6 | PR checklist: ledger row complete · no hotlinked URLs in code · no key material in diff or logs · AI-generated assets labeled. |
| 7 | If the key was exposed at any step: rotate in the Pexafy dashboard, re-register the secret, scrub the exposure. |

**Known limitations (honest status):** no asset has shipped through this pipeline yet; the ledger contains the template only. First entries are expected from the first UI issue that consumes the pipeline end-to-end (candidates: #163 image-led hero, #147 discovery screens — per #196 acceptance criteria).
